## 6. Coolify scheduled task (nightly)

`rentio-app` → Scheduled Tasks → New (or edit the existing one):

- **Name:** `nightly`
- **Frequency:** `15 7 * * *` (07:15 UTC; check the Coolify server timezone is UTC)
- **Container:** `rentio-app`
- **Command:**

```sh
node -e 'fetch("https://rentio-app.com/api/jobs/nightly",{method:"POST",headers:{"x-cron-secret":process.env.CRON_SECRET}}).then(async r=>{console.log(r.status,await r.text());process.exit(r.ok?0:1)},e=>{console.error(e);process.exit(1)})'
```

Why `node` and not `curl`: the app image is `node:22-slim`, which has no curl, and Coolify runs the task inside it. From any machine with curl, the same call is:

```sh
curl -fsS -X POST -H "x-cron-secret: $CRON_SECRET" https://rentio-app.com/api/jobs/nightly
```

Why 07:15 UTC: it is 00:15 MST / 01:15 MDT in El Paso and 01:15 CST / 02:15 CDT in Central Texas, so after local midnight all year. "Today" inside the job is always `today_el_paso()` (America/Denver), never UTC. The old `10 6 * * *` ran at 23:10 the previous evening all winter.

After saving, press **Run** once: expect `200` and a JSON with `per_org` (one entry per active company, each with `errors: []`). Press it again: all counts 0.

## 7. Smoke checklist (after deploy)

Phone width (375px) and desktop:

- [ ] `https://rentio-app.com/` loads; text is Plus Jakarta Sans (if #3 merged); no horizontal scroll at 375px.
- [ ] `/sign-in` loads, sign in as a company admin works.
- [ ] Dashboard loads; "Collected this month" equals Reports' income for this month (#24).
- [ ] Leases: a past-end active lease shows "Month-to-month" (#27).
- [ ] Payments: a manager sees **Void** on a confirmed payment; Invoices detail: a manager sees **Cancel invoice** (#61). Don't actually void real data; cancel the dialog.
- [ ] Automations page: a manager can toggle a setting and Save; Run now works and the "Last run" panel shows a new row for **this company only** (#55, #56).
- [ ] Tenant portal: sign in as a tenant, file a repair request; staff sees it with status "nueva", no cost/vendor (#25).

**Two-company isolation check** (the one that matters most). Needs a second, throwaway company whose only tenant email is an inbox you own:

1. As super_admin, create a test company (e.g. "QA Co", slug `qa-co`) with one property, one unit, one tenant (your own email) on an active lease, and one admin login (or act in it via the org switcher).
2. Note the real company's last run: `select org_id, max(started_at) from job_runs group by 1;`
3. Acting in **QA Co**, open Automations → **Run now**.
4. Check:
   ```sql
   select org_id, trigger, started_at from job_runs where started_at > now() - interval '10 minutes';
   select org_id, count(*) from notifications where sent_at > now() - interval '10 minutes' group by 1;
   select org_id, count(*) from late_fee_warnings where sent_at > now() - interval '10 minutes' group by 1;
   select org_id, count(*) from invoices where created_at > now() - interval '10 minutes' group by 1;
   ```
   Every row must be QA Co's `org_id`. The real company: no new `job_runs` row, no notifications/warnings/invoices touched.
5. Resend dashboard → Emails: only your own address, nothing to a real tenant.
6. Acting in the real company, its Automations "Last run" is unchanged.
7. Clean up: `update organizations set status = 'suspended' where slug = 'qa-co';` (or delete it if you prefer; rows cascade).

## 8. Rollback

- **App:** Coolify → `rentio-app` → Deployments → redeploy the previous image.
- **Database:** migrations 3 and 4 are safe to leave in place with older code. Migration 2 removed the no-argument functions older code calls; to bring them back, re-run these two re-runnable files in this order (the first recreates `late_fee_warnings_to_send()`, the second `nightly()`, `queue_*()` and `claim_notifications(int)`). The per-company versions stay alongside; PostgREST picks by argument names.
  ```sh
  for f in 20261028002200_nightly_job.sql 20261113000100_automations.sql; do
    { echo begin; cat "supabase/migrations/$f"; echo commit; } \
      | docker exec -i <rentio-db container> psql -U postgres -d rentio -v ON_ERROR_STOP=1 -q
  done
  ```
  (Tested on a throwaway Postgres 17: both exit 0 and the old and new functions coexist.) When you roll forward again, re-apply `20261121000100_automations_per_org.sql` by hand the same way, since `migrate-pending.sh` will `skip` it and leave the old all-companies functions in place.
- Last resort: restore the backup from step 2.
